Private Research Loop / Sources-First System Note

Private Search Research Assistant

Research usually slows down before analysis becomes difficult. The delay comes earlier, in the repetitive mechanics of searching across several indexes, opening near-identical pages, deciding which copy is canonical, skimming for the one paragraph that actually answers the question, and then rebuilding the provenance chain by hand so the answer can be trusted later. This assistant is designed to reduce that friction without hiding sources behind a polished paragraph. It aggregates search through SearXNG, filters and deduplicates candidates, extracts the content that matters, asks Gemini Flash for short summaries only after the evidence set is narrowed, and keeps citations and links at the center of the final response. Redis sits beside the loop so repeated or closely related queries do not force the same retrieval work every time.

Working Premise

This is not a general-purpose answer box. It is a constrained research instrument built to shorten the first pass while preserving inspectable source paths.

Search intake SearXNG fanout across multiple search sources
Selection logic Candidate filtering and deduplication before summarization
Reading step Page extraction rather than headline-only synthesis
Output rule Short answer, explicit citations, links retained
Acceleration Redis cache for repeated and near-repeated queries
Design bias Source visibility over conversational smoothness

Stage 01

Where does research actually stall?

The common failure mode in assisted research is not a lack of language generation. It is too much uninspected retrieval. A user starts with a narrow question, perhaps about a vendor policy, a feature announcement, an academic claim, or a market event. The search layer returns many URLs, but several are syndications, cached mirrors, translated reposts, forum paraphrases, or pages that quote the original without adding authority. The user is forced into mechanical sorting: open six tabs, dismiss four, read two, then reconstruct which facts came from which page. That work is cognitively expensive precisely because it is repetitive. It is easy to miss a relevant source because attention is spent on housekeeping.

A sources-first assistant therefore has to expose its retrieval mechanics rather than dissolve them into a fluent answer. It can remove repetitive work, but it should not remove the evidence trail. That is why this loop begins with SearXNG rather than a single opaque index. Aggregation matters because research questions often need range before ranking. One engine might surface official documentation first, another might surface recent reporting, and another might surface community traces. Pulling those result sets together gives the system a better candidate pool, but it also increases the need for careful consolidation. The design problem is not merely “find results.” It is “find overlapping results, decide which are truly distinct, and show the user where the answer came from.”

The result is less like a chatbot and more like a disciplined notebook assistant. It shortens the tedious first pass, but it leaves the seams visible: where the query went, what came back, which items were fetched, which were merged, and why the final answer cites the sources it does. That visibility is not decorative. It is the only way to make a quick research answer reusable in a serious workflow where someone may revisit the same question later and need to verify each supporting link.

A research loop earns trust by reducing clicks while increasing inspectability. If the user cannot see which source survived deduplication and why, the system has only hidden the friction, not resolved it.
Stage 02

What happens when one query fans into many source paths?

Once the question is normalized, the assistant sends it into a wider search fan. SearXNG acts as the broker, collecting result candidates from multiple search sources so the system is not beholden to a single ranking policy. That fanout is important for breadth, but it also creates immediate overlap. Several result paths may point to the same document through different URLs. Others may lead to summary pages that cite the original. Some may be strong only because they are recent, not because they are authoritative. The loop needs to keep that ambiguity long enough to inspect it, then narrow aggressively before any model writes prose.

The diagram below traces the intended path. One query branches through several search routes, lands in a shared candidate pool, then converges through filtering, extraction, and deduplication into a short answer block whose references remain attached. A Redis shelf sits beside the main flow because repeated work is part of the friction being removed. If the same question returns, or a close reformulation arrives, the system should be able to reuse prior search and extraction effort instead of repeating every network call.

At this point the assistant still does not claim to know the answer. It only knows the candidate landscape. That distinction is important. Search result pages are useful as routing data, not as evidence by themselves. The loop uses them to decide what to fetch next, what to cache, and what may already be a duplicate before expensive extraction begins.

Stage 03

Which pages deserve a full fetch?

Fetching everything is wasteful and often counterproductive. Many result lists contain pages that are obviously weak once basic metadata is considered: empty tag pages, navigational fragments, mirrors of the same article, AI-generated reposts, or link farms whose only value is that they happen to match the keywords. The system therefore performs candidate filtering before the content reader is invoked. This is where simple heuristics still do valuable work. Host reputation, path shape, repeated titles, suspiciously generic snippets, and obvious redirect patterns can all be used to remove low-value candidates without pretending the machine has fully interpreted the subject matter.

That filtering stage is intentionally modest. It is not there to decide truth. It is there to reduce reading load and to ensure the extraction budget goes to pages with a plausible chance of becoming evidence. In a sources-first loop, a strong official changelog, a primary documentation page, a well-cited article, and a carefully scoped community discussion may all survive, because each can support a different part of the answer. The key is that they are fetched for inspection as pages, not accepted as snippets. Search snippets compress too aggressively; they often omit qualifiers, dates, caveats, and surrounding language that determine whether a claim is actually relevant.

Redis helps here as well. When the same canonical URL appears in several searches, the assistant should not repeatedly fetch and extract it. A cached extract keyed to the canonical form of the page means the system can spend its latency budget on genuinely new material. That makes follow-up research feel cumulative rather than forgetful.

Why this matters

Search results are routing hints

The result page is a map of possibilities. It is not yet the evidence set, and it should not be summarized as though it were.

Practical filter

Weak candidates fail cheaply

Low-value hosts, duplicate titles, and empty content patterns should be removed before extraction consumes time and tokens.

Research bias

Primary beats derivative

Official or original sources are preferred because they keep the provenance chain short and easier to audit.

Stage 04

What survives once the page is extracted?

Extraction is where the assistant stops dealing in search abstractions and starts dealing with readable evidence. The purpose is not to scrape every byte of a page. It is to isolate the portion a human researcher would actually read: title, byline when relevant, publication hints, headings, body text, and sometimes tabular or list content if it carries the core claim. Navigation chrome, cookie notices, footer spam, and recommended-link noise are liabilities because they increase token load without increasing evidence quality. A compact, readable extract is therefore a research asset in its own right.

This stage also introduces an important humility rule: the summarizer should see less than the crawler can technically collect. The more indiscriminate the extracted payload, the easier it is for the final model to produce an answer that sounds grounded while actually leaning on peripheral text. Trimming the extract to what would survive a human first pass keeps the loop closer to research behavior. The assistant is effectively preparing a stack of annotated clippings, not training a model on the internet in miniature.

Short summaries generated with Gemini Flash belong after this cleaning step. The model is useful when it is given a bounded evidence set and asked to produce a concise account of what each source contributes. It is less useful when it is treated as a substitute for extraction. In this design, the model does not decide which pages exist, and it should not decide what the citation anchor is. It receives curated material and returns a short synthesis that still points back to the extracted sources. That order of operations matters because it narrows the model's freedom. The assistant is not rewarded for sounding comprehensive. It is rewarded for being traceable.

Readable extract shape

{
  "url": canonical_url,
  "title": page_title,
  "published_at": detected_date,
  "content": cleaned_text,
  "headings": selected_headings,
  "source_host": host
}

Cache key for extracted pages

extract_key = (
  "extract:" +
  sha256(normalize_url(canonical_url))
)

The extract is therefore the turning point in the loop. Before extraction, the system is still browsing possibilities. After extraction, it has assembled the raw material for evidence-aware summarization.

Stage 05

How do repeated URLs collapse into evidence rather than noise?

Deduplication is often described too casually, as if it were a trivial cleanup step at the end of search. In practice it determines whether the assistant behaves like a researcher or like a tab hoarder. Many duplicates are obvious only after the page is fetched. A press release may appear on the vendor site, a newsroom mirror, an investor portal, and a dozen copied articles. A documentation page may have localized versions, tracking parameters, and print views that look distinct at the URL level while being identical in substance. If those variants are allowed to enter summarization separately, the final answer will overcount agreement and undercount original evidence.

The design therefore needs dedupe keys that combine URL normalization with content-aware checks. Normalized host and path can catch superficial variance. Title similarity and content fingerprinting can catch mirrors that survive URL cleanup. When several records collapse into one evidence item, the assistant should preserve a canonical source, record alternates, and carry forward the strongest citation target. That target might be the official page, the original publication, or the most stable accessible copy, depending on the question.

This is where the system earns the right to summarize. Candidate filtering removed obvious weak links. Extraction produced readable material. Deduplication turns a pile of fetched pages into a coherent evidence set. Only now can the summarizer be asked for a short answer without quietly amplifying repetition.

Simple dedupe fingerprint

dedupe_key = (
  normalize_host(url) + "|" +
  normalize_path(url) + "|" +
  sha1(first_1500_chars(cleaned_text))
)

Merge rule sketch

if same_canonical_url or near_identical_text:
  keep = choose_preferred_source(group)
  keep.alternates.extend(other_urls)
  drop_rest(group)

The point of those keys is not mathematical perfection. It is operational discipline. A research tool gains reliability when it avoids counting the same claim three times simply because three indexes surfaced three wrappers around the same page.

Stage 06

When does summarization become assembly instead of invention?

By the time Gemini Flash is asked to produce a short synthesis, most of the hard work should already be done. The candidate set is filtered. The pages are extracted. Duplicates are collapsed. The remaining task is closer to editorial assembly than to open-ended generation. The model can now summarize the evidence set, compare the surviving sources, and produce a compact answer that preserves uncertainty where the sources diverge. That is a useful role for a fast model because it shortens reading time without pretending the model discovered the evidence itself.

The assembly step should be tightly scoped. Each statement in the answer ought to be backed by one or more extracted sources. If a source is used only for context and not for a factual claim, that should be clear in how the answer is phrased. If two sources conflict on a date, a version number, or a policy detail, the answer should not smooth over the discrepancy just to sound clean. Citation-minded research has a different standard from generic assistant copy. It values explicitness over tonal confidence.

That is also why the answer block should stay short. The more verbose the synthesis, the more likely it is to drift beyond the evidence set. A good research answer gives the user the main conclusion, the basis for that conclusion, and a path to inspect the underlying sources. It does not try to absorb the entire reading list into one totalizing paragraph.

Answer assembly example

answer = assemble(
  prompt=query,
  evidence=deduped_extracts,
  instructions="Summarize briefly. Cite every factual claim."
)

Redis shortens repeated research loops by reusing prior search pools and page extracts, while the answer itself stays grounded in the deduplicated evidence set rather than raw search snippets. In this design, SearXNG broadens intake, extraction narrows reading to relevant text, and Gemini Flash writes only after those sources have been consolidated. [1][2][3]

Stage 07

How are citations presented without becoming decorative?

Citations only matter if they remain easy to inspect. Many assisted systems add a bracketed number after the fact, but the citation target is vague, the link opens a search result instead of a source, or the supporting excerpt is impossible to find on the page. This design pushes in the other direction. The answer block should make each source visible as an object with a title, host, link, and a short statement of what that source contributes. In other words, the citation layer is not a footnote treatment added to generated prose. It is a parallel presentation of the evidence set that lets the user decide whether the synthesis is fair.

That means the source list should be as carefully assembled as the answer itself. The canonical source should be shown, alternates should be hidden unless useful, and repeated references should resolve to the same item instead of duplicating entries. A good citation panel also reveals what kind of source is being cited. Official documentation, company blog posts, community discussions, academic papers, and reporting all play different roles in research, and users should be able to see those differences quickly.

The model can be fast, the answer can be short, and the citations can still remain central. That is the design standard here. A private research assistant should make it easier to open the source, not easier to forget that the source exists.

  • [1] Canonical sourceOfficial or primary page used for the central factual anchor. Link retained, canonical URL preferred, extraction timestamp stored.
  • [2] Supporting sourceSecondary reporting or analysis that adds framing, comparison, or independent confirmation without replacing the primary citation.
  • [3] Qualified sourceLower-authority but still useful material, shown with its role made explicit so the user can weigh it correctly.
Stage 08

What operational constraints keep the loop honest?

A useful research assistant is defined as much by what it refuses to do as by what it automates. This loop should not present citation-free claims as settled fact. It should not summarize based only on search snippets when readable extracts are unavailable. It should not silently merge conflicting sources into a single confident sentence. And it should not let caching hide recency concerns. Cached search results and extracted pages must age out or be refreshed according to the kind of question being asked, because a product specification, a policy page, and a historical article each carry different update risks.

Operationally, that means the system needs boundaries. Fetch budgets prevent one question from exploding into an uncontrolled crawl. Extraction rules keep the evidence payload readable. Dedupe rules prevent repetition from masquerading as consensus. Summarization instructions keep Gemini Flash in a narrow lane: brief, grounded, and citation-aware. Cache policies decide when a prior answer is reusable and when the system must revisit retrieval. None of those controls are ornamental. They are what stop a retrieval loop from collapsing back into a generic answer engine.

The closing principle is simple: the assistant should make repeated research faster without making provenance weaker. If the user asks a similar question tomorrow, Redis should help the system avoid unnecessary work. If the evidence has changed, the assistant should say so or refresh. If a source cannot be extracted cleanly, the answer should show that limitation instead of bluffing. The loop is successful when the user feels the investigation has been accelerated but not obscured.

Operational constraints

  • Search aggregation broadens intake, but retrieval does not count as evidence until a page is fetched and extracted.
  • Deduplication happens before summarization so the model is not rewarded for repeating mirrored claims.
  • Gemini Flash is used for short summaries, not for unbounded synthesis over raw search results.
  • Citations and links remain visible in the final answer because the tool is meant to support research, not replace source reading.
  • Redis accelerates repeated or similar queries, but cache freshness must reflect the volatility of the topic.

This explainer describes a sources-first research loop with SearXNG aggregation, extraction, deduplication, short Gemini Flash summaries, visible citations, and Redis reuse. The governing idea is constant across every stage: reduce research friction without hiding where the answer came from.
